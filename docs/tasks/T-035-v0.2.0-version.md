## Goal

The workspace, the SDK, the core and every plugin move from `0.1.0` to `0.2.0`, and every changelog
has a `# 0.2.0` section dated the day of the release, so that the tags `v0.2.0` and
`plugin-<name>-v0.2.0` equal the Cargo versions the release and plugin workflows check.

## Scope

1. On a branch from `release/v0.2.0`: the version in every crate and plugin, and anything the release
   and plugin workflows compare with the tag; `Cargo.lock` by `cargo update --workspace --offline`.
2. The root `CHANGELOG.md` and each plugin's changelog: `Unreleased` becomes `0.2.0` with the date from
   `date -I`. The `Changed` section of the git plugin stays as written. A plugin with nothing new gets a
   0.2.0 section that says it is released with the 0.2.0 core for the 0.2.0 plugin interface.
3. Every `0.1.0` in the tree is judged: a fixture that pins the current version reads
   `CARGO_PKG_VERSION` instead of a literal; the README install example, the docs and the release
   notes' Install section say `0.2.0` where they mean the current release. A `0.1.0` that means that
   release (its changelog section, a fixture's arbitrary version, a third-party version) stays.
4. No other change.

## Done when

- `grep -rn '0\.1\.0'` over the tree prints only hits judged in the Resume point as meaning 0.1.0
  itself or an arbitrary version.
- `scripts/changelog-section.sh <file> 0.2.0` gives a non-empty section for the root and each plugin.
- fmt, clippy, test, deny and build exit 0 in the integration round on the `release/v0.2.0` tip that
  holds this branch (the lead's round; this task queues none).
- Do not edit docs/plan.md and push no tag; the lead tags.
